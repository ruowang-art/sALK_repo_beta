Architecture reference · genotyping & inventory tooling

Two Portals, One Colony

How a manually-downloaded Transnetyx CSV becomes a trustworthy inventory record and a printed cage card — and how a second, independent tool later consolidates the cage cards that pipeline produces. Written up as a systems & computer-science reference, not a user guide.

System relationship

Möuseley Kräs is the only producer of cage-card workbooks in this pipeline. Xol-Pots-Xol is a pure downstream consumer — a separate codebase, with its own pyproject.toml, src/, and tests, that reads workbooks Möuseley Kräs already wrote and never reaches back into its inventory, raw data, or source. 

flowchart LR
    TX["Transnetyx\n(external genotyping vendor)"] -->|manually downloaded CSV| MK["Möuseley Kräs\ngenotyping · inventory · cage cards"]
    MK -->|sparse Live Label\nworkbooks| XPX["Xol-Pots-Xol\ncage-card consolidator"]
    XPX -->|new, fuller workbook| OUT["Consolidated cage-card workbook"]

The arrow only runs one way: production, then consolidation. Neither tool imports the other's code.

01 · Möuseley Kräs

Purpose

Möuseley Kräs turns manually downloaded Transnetyx genotyping-result CSVs into a reconciled copy of the mouse inventory, an audit/exception report explaining exactly what happened to every record, and a Live Label weaning-card workbook for the vivarium. A second, independent portal registers brand-new litters into the inventory before they've been genotyped at all.

Its defining trait is safety: it is built to be trustworthy with irreplaceable lab records while remaining an ordinary local script and web app, with no database and no dedicated operations team behind it.

CS underpinnings

Nine ideas the design leans on

01

Functional core, imperative shell

Decisions — does this litter's math add up? does this genotype match? which cage-mates can share a card? — live in pure functions with no I/O, always returning the same answer for the same input. Orchestration (reading files, calling R, writing CSVs) is a thin shell around that core, so the hard logic is unit-testable without touching a real file.

02

Configuration as data

Which spreadsheet column holds which field, what genotype pattern counts as approved, which cell on the template maps to which output — none of it is hard-coded. It's declarative data in one config file, so the lab can re-point the tool at a differently-shaped spreadsheet without touching source.

03

Lenient parsing, zero-tolerance matching

Column names drift in real exports, so header lookup normalizes case and punctuation. But matching a mouse to a record is always an exact key match — no fuzzy identity matching, no auto-created rows. Cosmetic uncertainty is absorbed; identity uncertainty never is.

04

Fail-closed, explicit-outcome auditing

Every record gets a status from a closed set — READY, CONFLICT, MANUAL_REVIEW, NO_RESULT, PENDING_RERUN. There's no silent success path. A conflicting genotype is reported, never auto-resolved.

05

Checksum-verified copy-on-write

Before writing to the inventory, Möuseley Kräs hashes the existing file and takes a verified backup. Updates land on a new copy, never in place — copy-on-write scaled down to a single CSV, the same instinct behind journaling filesystems.

06

Idempotency via content hashing

Every raw input is SHA-256 hashed against a small index before processing. Re-running the same export twice is blocked by default — an idempotency key, the same idea a payment API uses to structurally prevent double-processing.

07

Process isolation across a language boundary

Probe-code translation runs in R; orchestration and matching run in Python. The two talk over a subprocess with an explicit argument list — never a shell string — and a handful of well-known CSV columns. Right tool per layer, narrow inspectable seam between them.

08

Two portals, one bounded context each

Cage Card Production and Mouse Inventory Update share the same backup and conflict-detection primitives but stay independent code paths — each owns one job and one input shape, rather than one form trying to do both.

09

Least-privilege external integration

The one live, shared external system it touches — a Google Sheet other lab members edit — gets a single opt-in, read-only overlay fetching exactly two fields, filling blanks only. It can't overwrite a local value, can't touch genotype, and a fetch failure degrades to a warning, never a failed run. Every cell it fills is now logged per mouse ID, not just an aggregate count.

02 · Xol-Pots-Xol

Purpose

Möuseley Kräs produces Live Label workbooks one small batch at a time, so a lab accumulates many sparse workbooks — each covering a handful of cages. Xol-Pots-Xol reads a set of those already-produced workbooks and merges compatible entries into fewer, fuller ones, without ever touching Möuseley Kräs's inventory, raw data, or template.

CS underpinnings

Six ideas the design leans on

01

Narrow coupling to one piece of domain content

Almost everything — strain names, dam/sire genotype text, most cells — is opaque text, copied through untouched. The one exception is the Kras locus, which the tool must understand to decide "same genotype." That knowledge lives in one small function backed by a named, versioned constant — not a general genotype parser.

02

Fail-open to "don't merge," never to a guess

When a genotype can't be confidently classified, the mouse goes to an explicit "unconsolidated" bucket and gets reported — the same instinct as Möuseley Kräs's own philosophy, arrived at independently in a separate codebase. Each one now carries a specific reason: unrecognized sex, blank strain, unsupported Kras genotype, or no usable DOB.

03

Pure read → transform → write-fresh

No workbook is ever edited in place. N sparse workbooks are read into memory, groups are computed, and one brand-new output workbook is written from scratch — side-effect-free on every input, trivially re-runnable.

04

Schema-as-contract via strict headers

Cells are read by fixed column index, but only after the header row is validated against an expected-headers contract. A stricter contract than Möuseley Kräs's header matching, because its own inputs are far more uniform — the right rigidity follows the actual variance in the input, not one rule everywhere.

05

Deterministic equivalence-class grouping

Mice are grouped by a composite key: normalized strain, Kras-normalized genotype class, and parents. "LSL-G12D/+" and "K/+" collapse to one canonical key — consolidation is equivalence-class partitioning, not string matching.

06

Output separates "done" from "needs a human"

The result workbook always has four sheets, each with one job: Sheet1 holds only successfully consolidated cages; Unconsolidated preserves every mouse that couldn't be grouped, kept structurally apart so it's never mistaken for a real cage; Review Needed lists each one with its source and reason; Report records counts and input-file hashes.

Flow

Consolidation flow

flowchart TD
    A["N sparse Live Label\nworkbooks, already produced\nby Möuseley Kräs"] --> B["Validate header row against\nexpected-headers contract"]
    B --> C["Read cells by fixed\ncolumn index into an\nin-memory mouse model"]
    C --> D["Normalize strain text\ntrim / casefold only"]
    C --> E["Kras-only genotype\nnormalization\nallowlist: +, K, LSL-G12D"]
    D --> F["Composite consolidation key:\nstrain + genotype class\n+ parents + ..."]
    E --> F
    F --> G{"Genotype key\nrecognized?"}
    G -->|no| H["Unconsolidated + Review\nNeeded sheets: mouse + reason"]
    G -->|yes| I["Group mice sharing\nthe same key -> Sheet1"]
    I --> J["Write the 4-sheet\noutput workbook"]
    H --> J

Unrecognized genotypes never block the run — they're set aside, visibly, with a named reason.

Status

Robustness pass (in response to external review)

An external review (via another coding assistant) proposed a robustness checklist after reading only this document, not the code. Auditing each item against the actual codebase found several already implemented (run manifests, dry-run mode, atomic backup writes) and confirmed the rest as genuine gaps. What actually got built:

MK

Möuseley Kräs

Regression tests for four previously-uncovered branches — existing-genotype CONFLICT, unknown-mouse-ID, missing-translated-column, duplicate-inventory-ID — plus a unicode-safety test. The run manifest now records app/Python/R versions, the config's path and checksum, whether the Sheets overlay is enabled, and a SHA-256 of every output artifact. The Sheets overlay reports exactly which mouse IDs and fields it filled.

XPX

Xol-Pots-Xol

Unconsolidated mice no longer blend into the same sheet as real consolidated cages — the clearest actual defect the review surfaced. The Kras grammar became a named, versioned contract instead of an inline dict. Eight new tests cover previously-blind spots: an unrecognized Kras string end-to-end, a reordered header row, duplicate mouse IDs, input-file immutability, and the new four-sheet output.

Deliberately deferred — each is a real design decision, not a bug fix: an inventory propose→approve→promote workflow step, new CLI subcommands (validate-config, inspect-run, summarize-audit), a formal config schema-version field, a Python/R dependency lock file, and a property-based testing framework.

Software versions & device compatibility

Both projects are local, single-user tools, developed and currently only tested on macOS. Neither has been run or verified on Windows or Linux — file-path conventions (e.g. the R executable path defaulting to /usr/local/bin/Rscript) assume a Mac.

Device compatibility

  • Development/test machine: macOS 26.6.2 (build 25G83), Apple Silicon (arm64).
  • Both are desktop CLI programs plus an optional local Flask web server — no mobile or tablet app, and neither can run natively on a phone/tablet.
  • The web server binds to 127.0.0.1 by default. It can be pointed at the Mac's LAN address (automouse serve --host <lan-ip>) so another device on the same network — e.g. an iPad — can reach it in a browser, but the Mac still has to be the one running the server the whole time; there's no offline or standalone mode for a second device, and no built-in authentication, so only do this on a trusted network.
  • Apple Silicon vs. Intel: nothing in the codebase is architecture-specific — R and Python are both installed system-wide as arch-appropriate builds by their own installers — but an Intel Mac has not been separately verified.
